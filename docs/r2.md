# Media in Cloudflare R2

Uploaded media (`/originals`, `/streams`, `/teasers`, `/thumbs`, `/avatars`) can live in a
Cloudflare R2 bucket instead of the node's disk. Full episodes of 1–1.7 GB filled the live
node's 50 GB disk on 2026-11-03; with R2 the node keeps only what it's still working on.

The code is in `media_store.py`. Nothing changes until the `GFC_R2_*` settings are filled in.

## How it works

| Node | Settings | What it does |
|---|---|---|
| Local (default) | none | Everything on this disk, as before. |
| Official | all five `GFC_R2_*` | Stores new media in the bucket and deletes the local copy. |
| Community | only `GFC_R2_PUBLIC_URL` | Read-only. Serves media from the bucket and refuses uploads. |

- **Apps don't change.** Feed JSON still says `/originals/<file>`, `/thumbs/<file>` and so
  on. The node serves a file from its own disk when it has one (Range requests work as
  before). Otherwise it answers `302` to `GFC_R2_PUBLIC_URL/<kind>/<file>`. Browsers,
  `<video>` and `<img>` follow redirects, and so do the app HTTP clients.
- **When a file moves:** after it's processed. A video or big audio file moves once its
  streaming copy and thumbnail exist. Anything else moves right after upload, and an
  avatar right after it's saved. The node uploads the file and then checks it: the bucket
  copy must match the local size and MD5 ETag, and R2 also rejects a body whose SHA-256
  doesn't match the signed one. Only then does the node record the file in the
  `media_objects` table and delete the local copy. If any step fails, the node keeps the
  local copy and logs `[MediaStore] ... keeping the local copy`.
- **Hourly sweep:** an official node also moves anything left behind every hour, such as
  files synced from peers or a restart in the middle of an upload. It skips files less than
  10 minutes old and originals that are still waiting for a streaming copy. After a day
  without a streaming copy (for example, no ffmpeg), the original moves anyway.
- **Community nodes** can't post or change avatars (`403` with "This is a community GFC
  node..."). Posts need an official node, the only kind that holds the write token. I chose
  refusing over forwarding uploads to an official node: the post is signed with the
  poster's wallet key, which lives on the node they're logged in to, so forwarding would
  mean moving keys or sessions between nodes. A community node still serves the files it
  has on disk (synced from peers) and redirects for everything else.

### What never goes to the bucket

The bucket's public URL exposes the **whole** bucket, so a "private prefix" wouldn't be
private. Gated files stay on the official node's disk, behind the gates that already exist:

- **The full clip of a GFC Exclusive:** `/originals/<file>` and its `/streams/` copy. These
  still need a signed link from `GET /seeds/{id}/play` (`exclusive.py`). The public teaser
  and thumbnail do go to the bucket.
- **Downloads (`.zip`):** they can't be fetched until the virus scan passes, and they're
  rescanned every day (`filescan.py`). The scanner needs the file on disk, and a file that
  fails a later rescan must disappear at once. Their thumbnails go to the bucket.

The node never redirects a gated path to the bucket, even when the file is missing. If
exclusive videos start taking a lot of space, a second, non-public bucket with presigned
URLs is the next step. The code isn't written for it yet.

## Cloudflare setup (dashboard)

1. **Create the bucket.** In the Cloudflare dashboard, open **R2 Object Storage** →
   **Create bucket**. Name it (for example `gfc-media`), leave the location on
   *Automatic*, and click **Create bucket**. (The first time, R2 asks you to add a payment
   method and enable R2. The free tier covers 10 GB of storage, and egress is free.)
2. **Turn on public access.** Open the bucket → **Settings**:
   - **Custom Domains → Add** a domain you already manage in Cloudflare, such as
     `media.<your domain>`. Use this for production, because it can be cached and isn't
     rate-limited. Or:
   - **Public Development URL (r2.dev) → Enable**, and type `allow` to confirm. You get
     `https://pub-<id>.r2.dev`. That's fine for testing, but Cloudflare rate-limits it.

   The address you get is `GFC_R2_PUBLIC_URL`, with no trailing slash.
3. **CORS** (so the web app can fetch media from the bucket's domain). Under bucket
   **Settings → CORS Policy → Add CORS policy**, enter:

   ```json
   [{"AllowedOrigins": ["*"], "AllowedMethods": ["GET", "HEAD"], "AllowedHeaders": ["Range"],
     "ExposeHeaders": ["Content-Length", "Content-Range", "Accept-Ranges", "ETag"], "MaxAgeSeconds": 86400}]
   ```
4. **Create an API token for the official node.** On the **R2 Object Storage** overview,
   click **Manage API tokens** → **Create Account API token**:
   - Name: for example `gfc-node-media`
   - Permissions: **Object Read & Write**
   - Specify bucket(s): **Apply to specific buckets only** → select `gfc-media`
   - TTL: Forever (or a date you'll remember to rotate by)

   Click **Create API Token**. The next page shows the **Access Key ID** and the **Secret
   Access Key** only once. Put them straight into the node's settings in step 5; don't
   paste them anywhere else. The **Account ID** appears on the same page, inside the S3
   endpoint `https://<ACCOUNT_ID>.r2.cloudflarestorage.com`, and on the R2 overview.

   Community nodes never get a token: only official nodes do.
5. **Give the settings to the node.** This opens the settings file in an editor and
   restarts the node:

   ```powershell
   ssh -t gfc-node gfc config
   ```

   Fill in the five values. The first time, also add `GFC_R2_KEEP_LOCAL=1` (see the next
   section):

   ```
   GFC_R2_ACCOUNT_ID=<account id>
   GFC_R2_BUCKET=gfc-media
   GFC_R2_ACCESS_KEY_ID=<access key id>
   GFC_R2_SECRET_ACCESS_KEY=<secret access key>
   GFC_R2_PUBLIC_URL=https://media.<your domain>
   GFC_R2_KEEP_LOCAL=1
   ```

   The log shows `[MediaStore] Media storage: r2 (keeping local copies)` at startup.
   If a write setting is missing, the node says so and doesn't write to the bucket.

## Moving the existing files

```powershell
ssh gfc-node gfc media status
ssh gfc-node gfc media migrate --dry-run
```

`migrate --dry-run` lists what would be uploaded and which files stay on the node
(exclusive clips and downloads). Then do the real copy. It takes hours for tens of GB, so
run it as a background job that survives a dropped connection, and follow its log:

```powershell
ssh gfc-node systemd-run --unit gfc-media-migrate gfc media migrate --keep-local
```

```powershell
ssh gfc-node journalctl -u gfc-media-migrate -f
```

`--keep-local` uploads and verifies every file but deletes nothing. Spot-check a few posts
in the app and the web feed. Then run the same command without `--keep-local` (systemd needs a new unit name, such as `gfc-media-migrate2`). It doesn't
upload again: files already verified (same size, unchanged since) are only deleted
locally. Finally, remove `GFC_R2_KEEP_LOCAL=1` with `gfc config`. A failed file is listed
as `failed` and keeps its local copy, and the command exits non-zero. Run it again later
to retry.

On the command line: `python media_store.py status | migrate [--keep-local] [--dry-run]`.

## Limits and known gaps

- **Size limit:** one upload is at most about 4.99 GiB on R2 (no multipart upload here).
  The node's post limit is 5 GiB (`GFC_MAX_UPLOAD_MB=5120`), so a file in that last 5 MiB
  fails to upload and stays on disk, logged.
- **P2P file sync** (`sync_engine.py`, not changed here): an official node answers "not
  found" when a peer asks for a file that's in the bucket. Its own missing-file recovery
  still asks peers for files it has moved. If a peer has a copy, the file is downloaded
  again and the next sweep deletes it without uploading again. A follow-up for the
  peer-sync work should treat files listed in `media_objects` as present.
- Posts removed by moderation keep their files, in the bucket as on disk before.
- Posts deleted by their creator (`DELETE /seeds/{id}`, `seed_deletions.py`) lose their
  files on every node: the official node deletes its bucket objects and local copies,
  community nodes their synced copies. A bucket delete that fails is retried at startup
  and by the hourly sweep, and the sweep never uploads a deleted post's late files.
- Rotating the token: create a new one (step 4), update it with `gfc config`, then delete
  the old token in the dashboard.
