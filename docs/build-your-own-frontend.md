# Build your own GFC front end

The official GFC app (Unreal, Android) is just one client of the node's REST API.
Anything that can make HTTP requests can be a GFC front end: a web page, a
phone app, a bot, a script. This guide covers what you need to know to build
one that is safe for your users.

The complete, always up-to-date reference is generated by the node itself:

- **`/docs`**: interactive Swagger UI. Click **Authorize**, paste a token, and
  try every endpoint from the browser.
- **`/openapi.json`**: the machine-readable OpenAPI schema. Feed it to a client
  generator, or paste it into your AI coding assistant as context.

Examples below use `http://127.0.0.1:8000` (a local node). A public gateway
node works the same way.

## The one rule: keys never leave the node

A wallet's ID is its Ed25519 public key, and its **private key stays on the
user's home node**, encrypted at rest. There is no endpoint that returns a raw
private key. Your front end never sees, stores or handles wallet keys.

Instead, your front end asks the node to act, and the node signs:

- `POST /transactions/create`: the node signs the transfer with the sender
  wallet's key.
- `POST /seeds/upload`: the node signs the seed with the creator's reward
  wallet, so rewards for it can only ever go to that wallet.

Don't try to do your own signing or build transactions client-side. Peers
reject anything that isn't signed by the right key, and you'd have to hold
keys you shouldn't.

## Authentication

### Log in

```bash
curl -X POST http://127.0.0.1:8000/auth/login \
  -F username=alice -F password='correct horse battery staple'
# {"ok": true, "token": "Xy3...", "user": "alice"}
```

`POST /auth/register` takes the same fields (plus optional `first_name`,
`last_name`, `email`, `phone`) and also returns a token.

### Send the token as a Bearer header

```bash
curl http://127.0.0.1:8000/users/me -H "Authorization: Bearer Xy3..."
```

```js
const res = await fetch(`${NODE}/users/me`, {
  headers: { Authorization: `Bearer ${token}` },
});
```

Every authenticated endpoint accepts the header. Older clients pass the token
as an `api_token` form field, query parameter or JSON field instead. That still
works, but **don't use it in new front ends**: query strings end up in server
logs, browser history and referrer headers. If a request carries both, the
header wins.

Tokens expire (30 days for login tokens). A `401` means the token is missing,
invalid, expired or revoked: send the user back to login.

### Scoped tokens

A login token can do everything, including spending. If your front end doesn't
need all of that, or you're handing a token to someone else's code, mint a
**limited token**:

| Scope | Allows |
|---|---|
| `read` | Personal reads: `/users/me`, `/bookmarks`, `/seeds/mine`, the personalised feed (liked/bookmarked flags) |
| `post` | Uploading seeds, likes, comments, bookmarks, editing the profile and avatar, creating wallets, phone verification, recording plays |
| `spend` | `/transactions/create`, `/wallets/export`, `/wallets/import` |

Public data (`/feed`, `/search`, `/wallets/{id}`, `/transactions/history`,
comments, share pages) needs no token at all.

A token without the needed scope gets `403`.

```bash
# Needs a full-scope (login) token AND the password
curl -X POST http://127.0.0.1:8000/auth/tokens \
  -H "Authorization: Bearer $LOGIN_TOKEN" \
  -F password='correct horse battery staple' \
  -F scopes='read post spend' \
  -F label='my tipping widget' \
  -F expires_in_days=7 \
  -F spend_limit_cents=500
# {"ok": true, "token": "...", "id": "3f9a...", "scopes": ["read","post","spend"],
#  "spend_limit_cents": 500, "expires_at": "...", "spent_today_cents": 0, ...}
```

- `scopes`: any of `read`, `post`, `spend`, separated by spaces or commas.
- `expires_in_days`: up to 365. Default 30.
- `spend_limit_cents`: optional. Caps what this token can transfer per UTC day,
  in cents (500 = 5 GFC). Going over gets `403`. A failed transfer doesn't
  count against the limit.
- The token is shown **once**. Only its hash is stored.

Limited tokens can still sign: a token with `post` can sign seeds, and a token
with `spend` can sign transfers, without the password. A `read`-only token
can't unlock wallet keys at all.

Manage tokens:

- `GET /auth/tokens` (full-scope token): lists your tokens with their `id`,
  label, scopes, limit, expiry and today's spend. Tokens themselves are never
  shown. `current: true` marks the token you called with.
- `DELETE /auth/tokens/{id}`: revokes a token immediately. Any token can
  revoke itself (that's "log out"). Revoking another token needs a full-scope
  token.

**Suggested pattern:** log in, mint a token with only the scopes your front end
needs, keep that one, and drop the login token (`DELETE` its id). Give spending
tokens a sensible `spend_limit_cents`.

## Wallets and transfers

```bash
# Create a wallet (post scope). The ID is the wallet's public key.
curl -X POST $NODE/wallets/create -H "Authorization: Bearer $T" -F name=main

# Balance (public)
curl $NODE/wallets/<wallet_id>
# {"id": "...", "name": "main", "balance": 100.0, "balance_cents": 10000}

# History (public)
curl "$NODE/transactions/history?wallet_id=<wallet_id>"

# Transfer (spend scope). JSON body. The node signs it.
curl -X POST $NODE/transactions/create -H "Authorization: Bearer $T" \
  -H "Content-Type: application/json" \
  -d '{"sender": "<your wallet>", "recipient": "<their wallet>", "amount": 2.5, "reason": "tip"}'
```

Amounts are in GFC with two decimals. Balances are computed from the signed
ledger; `balance_cents` is the exact integer value. The sender wallet must
belong to the token's user, or the node returns `403`.

A user's first wallet receives the 100 GFC new-user grant, but only once their
phone is verified (see below).

## The backup prompt (please show it)

Wallet keys live on one node, encrypted with a key derived from the user's
password. **If the user forgets their password or loses that node's data, their
wallets are gone**, unless they made a backup. There is no reset.

Every front end that creates wallets should prompt the user to back up, ideally
right after the first wallet is created and again whenever a new wallet is
added:

```bash
curl -X POST $NODE/wallets/export -H "Authorization: Bearer $T" \
  -F password='correct horse battery staple' \
  -F backup_passphrase='a long passphrase of 12+ characters'
```

This returns a passphrase-encrypted JSON backup (scrypt + AES-GCM). Let the user
save it as a file, and tell them plainly:

- Keep the file and the passphrase somewhere safe and separate.
- Anyone with both can spend the wallets.
- Without them, a forgotten password means lost funds.

`POST /wallets/import` (`backup_passphrase`, `backup` as the JSON text) restores
it on any node.

Export needs the `spend` scope and the password, so a stolen token alone can't
take a backup.

## Uploads

```bash
curl -X POST $NODE/seeds/upload -H "Authorization: Bearer $T" \
  -F file=@ship.glb -F thumbnail=@ship.jpg \
  -F title='My ship' -F description='Low-poly cruiser' -F tags='3d,ship'
```

- `file` is required. `thumbnail` is an optional JPG you generate client-side.
- `reward_wallet` is optional and defaults to the user's oldest wallet on this
  node. The node signs the seed with that wallet. `rewards_enabled: true` in the
  response means it's signed and can earn.
- Media is served from the returned `full` (`/originals/...`) and `thumb`
  (`/thumbs/...`) paths, relative to the node.

## The feed

- `GET /feed`: every seed, newest first. With a `read` token, each item also
  has `liked` and `bookmarked` for that user.
- `GET /search?q=...`: seeds and transactions matching all keywords.
- `GET /seeds/{id}/comments`, `POST /seeds/{id}/comments` (`text`),
  `POST /seeds/{id}/like`, `POST /seeds/{id}/bookmark` (toggles),
  `GET /bookmarks`, `GET /seeds/mine`.
- `GET /users/{username}` for public profiles, `GET`/`POST /users/me` and
  `POST /users/me/avatar` for the user's own.

### Rewarded plays

When a user plays someone else's media, call:

```bash
curl -X POST $NODE/seeds/<seed_id>/played -H "Authorization: Bearer $T"
```

The creator's reward wallet is paid if the rules allow it. A play only pays if
the viewer's phone is verified, their account is at least 24 hours old, and
they haven't already paid that creator today. The response says whether it
credited, and why not.

**Unofficial clients rely on phone verification, not Play Integrity.** The
official Android app may add Google Play Integrity attestation on top, but a
third-party front end can't produce that. For your users, the phone check (and
the per-viewer, per-creator limits) is what makes their plays count. Don't try
to fake attestation.

## Share pages

A gateway node serves a public, read-only page for every seed it has synced:

- `GET /p/{seed_id}`: an HTML page with Open Graph and Twitter Card tags, so
  links show a preview card on X, Discord and messaging apps.
- `GET /p/{seed_id}/share`: JSON with the page `url`, suggested `text`, an
  `x_intent_url` for posting to X, and an `app_link` deep link.

Use `/share` to build your share button. Point people at the gateway's
`https://galacticfederation.tech/p/...` URL, not at a home node.

## Phone verification and Turnstile

Phone verification unlocks the 100 GFC grant and play rewards. One phone
number per account, and only a keyed hash of the number is stored.

```bash
# 1. Send a code (post scope)
curl -X POST $NODE/verify/phone/start -H "Authorization: Bearer $T" \
  -F phone=+14155550123 -F turnstile_token=<token from the widget>

# 2. Check it
curl -X POST $NODE/verify/phone/check -H "Authorization: Bearer $T" \
  -F phone=+14155550123 -F code=123456
# {"verified": true, "grant": 100.0, ...}
```

Numbers are E.164 (`+` and country code). VoIP numbers are refused, and code
requests are rate-limited.

Nodes that run verification publicly (the hosted verification node) set
`GFC_TURNSTILE_SECRET` and require a **Cloudflare Turnstile** token on
`/verify/phone/start`, to stop SMS pumping. Your front end shows the Turnstile
widget with the node operator's **site key**, then sends the token it produces
as `turnstile_token`. Without a valid token the node returns `403` and sends no
SMS. Local nodes without the secret skip this check.

## Calling a node from a web page (CORS)

Browsers block cross-origin requests unless the node allows the page's origin.
By default a node allows **none** (same-origin only). A node operator who wants
to allow chosen web front ends sets:

```bash
GFC_CORS_ORIGINS="https://my-frontend.example,https://other.example"
```

Allowed origins may send the `Authorization` and `Content-Type` headers with
`GET`, `POST` and `DELETE`. Cookies aren't used, so credentials are off. Native
apps, scripts and server-side code aren't affected by CORS.

## Checklist

- [ ] Send tokens in the `Authorization: Bearer` header, never in URLs.
- [ ] Mint a token with only the scopes you need, and a spend limit if it can spend.
- [ ] Store tokens like passwords (not in shared logs or analytics).
- [ ] Never ask for, store or handle wallet private keys. Let the node sign.
- [ ] Prompt users to export a wallet backup and keep it safe.
- [ ] Handle `401` (log in again) and `403` (missing scope or limit reached).
- [ ] Support phone verification and, on public nodes, Turnstile.
- [ ] Share with `/p/{id}` links from the gateway.
